<interfaces>
Writer contract (RESEARCH Pattern 4, executed there against PostgreSQL 16). One transaction per batch, in this order: (1) accounts upsert by pseudonym returning ids (ON CONFLICT DO UPDATE with a no-op set so RETURNING yields existing rows); (2) claims upsert by claim_key returning ids; (3) cascades insert for new roots ON CONFLICT (root_uri) DO NOTHING, selecting existing ids on conflict; (4) events insert ON CONFLICT (uri) DO NOTHING RETURNING uri (rowcount is -1 for executemany, so inserted and duplicate counts come from RETURNING); every row dict is built by ONE function so every dict has the identical key set (SQLAlchemy takes the key set from the first dict); (5) mark touched cascades enrich_dirty and apply the overflow tally of the paragraph below; (6) tombstones: UPDATE events SET deleted_at, account_id NULL, occurred_at NULL, text NULL, claim_id NULL, lang NULL WHERE uri = ANY(:keys) AND deleted_at IS NULL RETURNING cascade_id, edge_kind (a second identical tombstone touches 0 rows); a tombstoned root sets cascades.root_deleted_at; (7) account-wide tombstones: resolve accounts.id by pseudonym, then the same UPDATE WHERE account_id = :id AND deleted_at IS NULL; (8) the checkpoint: INSERT ... ON CONFLICT (source) DO UPDATE SET cursor_time_us = GREATEST(existing, excluded), updated_at = now(). Inserts come before tombstones so a create and its delete in one batch end as a tombstone. Root rows: edge_kind root, inferred false, parent_state none, cascade_id set, text only when RETENTION_TEXT_DAYS is greater than zero, lang en, claim_id from the claim upsert. Other rows: parent_state orphan until enrich resolves them (plan 03-06), inferred true only for reposts, text NULL, lang NULL. A cascade row is created with first_event_at and last_event_at equal to the root's observed_at and tracking_ends_at equal to observed_at plus TRACK_ROOT_TTL_HOURS. Claim for a root: kind social_link, url_canonical the matching canonical URL (allowlisted, or matched through option B), link_domain its host, text the publisher's link-card title (publisher text, not personal), text_hash and claim_key as lowercase base32 truncated SHA-256 digests (26 characters) of the kind and the canonical URL.

Tracked set (D-14): in memory, a map from uri key to (cascade id, tracking end) for the stored events of cascades whose tracking window is open, loaded from the database at run start for cascades with tracking_ends_at later than the resume cursor minus the rewind, extended as rows are inserted and pruned as windows close. Reply: cascade of reply.parent if stored, else the cascade of reply.root if stored (an orphan in that cascade); when both are stored in different cascades the parent's cascade wins and `cascade_conflict` is counted. Quote and repost: the cascade of the target. Refusal reasons are stable strings counted per reason: untracked, tracking_ended, cap_active_roots, cap_total_events, overflow, plus the selection reasons. A delete lookup is by key against the database, not against the open-window index.

Duplicates before caps (SC3): the Decider tests membership of the event's own key in the index FIRST; a key that is already stored is a duplicate (counted, never refused and never counted as overflow), so redelivery by a rewind, a replay or a restart cannot be mistaken for a new event at a capped cascade. Overflow tally (D-14, D-20): an event refused only because its cascade holds TRACK_MAX_EVENTS_PER_CASCADE stored events is not stored, so ON CONFLICT cannot absorb its redelivery; the tally therefore uses `cascades.overflow_through_us` (bigint, NULL until the first overflow, from the baseline of plan 03-03), the stream-time high-water mark of the overflow events already counted: an overflow refusal increments the cascade's overflow_count only when its stream time in microseconds is strictly greater than the mark, where the mark is the larger of the value loaded into the index at run start and the batch's own pending mark (so repeated deliveries inside one batch count once), and the batch transaction applies per cascade `UPDATE cascades SET overflow_count = overflow_count + :n, overflow_through_us = :t WHERE id = :id AND (overflow_through_us IS NULL OR overflow_through_us < :t)` with bound parameters; the in-memory mark advances only after the commit. A replay, a 30 s rewind, a restart and a kill-and-resume therefore leave both columns unchanged: the tally is a lower bound that redelivery cannot inflate, and it can undercount events delivered out of stream-time order or sharing a microsecond with an already counted one (the API says 'at least', plan 03-07).

Option B (OD-3, D-13): `load_known_claim_urls(connection, limit=KNOWN_CLAIM_URL_LIMIT)` in writer.py returns the frozenset of url_canonical of claims of kind news_headline with a non-null URL (newest first, a named limit constant of 20000, bound parameters). When `policy.track_seed_claim_url_match` is true the run loop calls it at start and again every 50 batches (together with the capacity check) and hands the set to the Decider, which passes it with the flag to `seed_decision`; when the flag is false the claims table is never queried. A root accepted this way is counted as seed_claim_url_match, its claim is the usual social_link claim, and every hygiene rule (language, adult labels, shorteners, top-level only) still applies.

Run model (D-10): `python -m truthtrail.ingest run` stops at the first of --max-seconds (default INGEST_MAX_SECONDS), --max-events frames processed, --max-stored rows written, the STORE_MAX_EVENTS_TOTAL cap and, checked at start and every 50 batches, pg_total_relation_size of the application tables at DB_STOP_PERCENT of DB_BUDGET_BYTES; batches flush at INGEST_BATCH_ROWS rows or INGEST_BATCH_SECONDS, a checkpoint-only transaction is written when the cursor advanced and no rows were stored; time bounds use a monotonic clock, never stream time. ingest_runs gets a row at start (status running) and its final status (ok, capacity_reached, interrupted, source_failed, db_failed), stop reason, counters (a JSON object of counts by name), last_time_us, the gap fields and the error class name only. The checkpoint source name is bluesky for live and bluesky-replay for replay, so a replay never moves the live cursor. A checkpoint older than INGEST_MAX_RESUME_AGE_HOURS (live mode only) starts at the tip and records a gap. One advisory lock per command (a constant key per command) makes runs single-flight; a second run exits 6.

Live protocol facts (RESEARCH Pattern 2, Pattern 12, F-02, F-03, F-04, F-20): connect with `websockets.asyncio.client.connect(url, subprotocols=[Subprotocol("xrpc.v1.json")], max_size=2 MiB, max_queue=1024, user_agent_header=..., open_timeout=10)` and websockets' default proxy handling (loopback tests pass proxy=None); its built-in reconnect iterator reuses the same URI and cannot carry a new cursor, so the source implements its own loop; an HTTP rejection surfaces as InvalidStatus whose response body carries the JSON error name; a frame above max_size closes the connection with 1009 and a reconnect would meet the same frame again, which is why maxMessageSizeBytes is sent (1048576) and 1009 is fatal; `{"$type":"error","error":"ConsumerTooSlow"}` is a normal reconnect cause; the writer must keep the reader moving (batch flush in a worker thread via asyncio.to_thread gives natural backpressure).
